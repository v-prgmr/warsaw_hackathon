AR GLASSES BRIDGE - SETUP FOR THE UBUNTU LAPTOP CONNECTED TO THE G1
====================================================================
(repo v-prgmr/warsaw_hackathon, branch claude/ar-glasses; details in ar_glasses/README.md
 and AGENTS.md section 27)

WHAT THIS IS
------------
The Snap Spectacles already have our Lens installed (it was pushed from Lens Studio on Windows;
it stays on the glasses). The Lens is a WebSocket CLIENT. It connects over Wi-Fi to a SERVER
("the bridge") at:

    ws://<THIS LAPTOP'S Wi-Fi IP>:8787        (port 8787 is fixed in the Lens, path "/")

The bridge runs on THIS Ubuntu laptop, because this laptop already sees our ROS 2 topics from
the G1 over Ethernet. Nothing is installed on the robot.

    Spectacles --Wi-Fi--> this laptop: bridge on :8787 --ROS 2--> our stack --Ethernet--> G1

Windows is only needed to change the Lens itself. Not needed to run anything here.


NETWORK REQUIREMENTS
--------------------
- Keep the Ethernet link to the robot as it is (192.168.123.x, our usual setup).
- Put the laptop's Wi-Fi on the SAME network as the glasses. Event Wi-Fi often blocks devices
  from talking to each other -> use a phone hotspot or our own router for laptop + glasses.
- Find the Wi-Fi IP:            ip -4 addr show   (the wlan/wlp... interface)
- If a firewall is on:          sudo ufw allow 8787/tcp
- Test from a phone on the same Wi-Fi: open http://<laptop IP>:8787 in the browser.
  A short "Failed to open a WebSocket connection" / "426" page = reachable. Spinning = blocked.

---------------------------------------------------------------------------
    cd ~/warsaw_hackathon

a robot box, a room point cloud and two labelled demo POIs appear. Stop with Ctrl+C.
Optional check:  cd ar_glasses/mock_bridge && python3 -m pytest   -> 10 passed


STEP 2 - THE REAL BRIDGE: g1_ar_bridge (NOT BUILT YET, being written on claude/ar-glasses)
------------------------------------------------------------------------------------------
Same WebSocket server on :8787, but fed by our ROS 2 topics instead of simulated data.
It runs inside our usual ROS 2 Humble environment (Docker image / scripts/run_humble.sh), on the
robot's DDS domain, next to g1_sensors + g1_mapping. It only READS topics:

    robot pose      TF  map -> torso_link / robot_center   (RTAB-Map + g1_sensors)
    LiDAR map       /cloud_map                             (g1_mapping)
    Nav2 path       /plan                                  (when Nav2 runs)
    POIs / boxes    semantic_query output (frame_id = map) -> drawn in the glasses as
                    labelled markers and 3D boxes (Lens "draw_world_annotation" skill)

Safety (AGENTS.md sections 19 and 25): navigation goals and commands sent from the glasses are
IGNORED by default. The bridge never publishes /cmd_vel. Do NOT run the upstream Dimensional OS
stack (launcher/start.sh) against the real G1: it is a second robot stack and can walk the robot.

Expected run command once it exists (will be confirmed in ar_glasses/README.md):
    ros2 launch g1_ar_bridge ar_bridge.launch.py


WEBSOCKETS vs FASTAPI
---------------------
Either works: the Lens only needs a WebSocket server on port 8787, path "/", that speaks the
Lens protocol v19 (the Lens rejects any other version):
  - JSON text messages, each ending with "\n" (hello, runtime_snapshot, pose, path, ...)
  - binary LiDAR frames: byte 0x01, float32 timestamp, then float16 x,y,z per point
  - binary camera frames FROM the Lens: "ARF1" + uint32 header length + JSON header + JPEG
  - frame: metres, Y up, robot +X forward, quaternions [x, y, z, w]
The reference implementation is ar_glasses/mock_bridge/mock_bridge.py.
Plan: g1_ar_bridge = rclpy node + the "websockets" library (one process, no uvicorn, built with
colcon like our other packages). FastAPI/uvicorn only if we later also want HTTP pages or a REST
API (e.g. a POI list in the browser); it would then run in the same ROS 2 environment.


APRILTAG (aligning the glasses with the robot)
----------------------------------------------
We have ONE tag: AprilTag 36h11, ID 0. That matches the upstream G1 default exactly:
tag ID 0 on the G1 CHEST panel, facing forward, 70 mm printed (56 mm black square),
centre ~ (x 0.072, y 0.0, z 0.178) m from the pelvis. One tag is enough (full 6-DoF pose).
  - Print it at 70 mm outer size (or measure the black square and tell us), glue it flat to card.
  - Mount it flat on the chest without covering the OAK-D, LiDAR, cameras or vents (sec. 25.2).
    If the OAK-D takes that spot, put it elsewhere and MEASURE its position vs torso_link.
  - Until g1_ar_bridge supports it: use "Manual Placement" in the Lens (no tag needed).
