# Laptop anchor for Spectacles (2024)

This is the G1-free physical test fixture. The [tag SVG](apriltag_36h11_id0_160mm.svg)
is AprilTag 36h11, ID 0. Its **black square** is 160 mm at 100% print scale.
The white SVG canvas is 180 mm; the surrounding paper adds more white margin.
It was generated by [generate_tag.py](generate_tag.py), not hand-drawn.
Its orientation now matches the
[AprilRobotics ID 0 reference image](https://github.com/AprilRobotics/apriltag-imgs/blob/master/tag36h11/tag36_11_00000.png).

Print at **actual size / 100%** (turn off “fit to page”), then measure the
black square with a ruler. If it is not exactly 160 mm, update `tag.size_m`
in `g1_ws/src/spectacles_localization_ros/config/laptop_anchor.yaml` to the
measured value. Alternatively display it full-screen on the laptop, but
measure the black square on the physical screen: browser zoom and display DPI
do not guarantee 160 mm. Avoid glare, reflections, and the screen going dark.

Fix the tag rigidly to the laptop or a stand that will **not move** during the
test. The coordinate frame named `laptop` is deliberately defined at the
tag's centre, with the printed tag's X/Y/Z axes. This is not the computer's
internal chassis frame; a separate measured transform would be needed for
that. The YAML's `T_laptop_tag = identity` is therefore a frame definition,
not a guessed calibration.

Do the existing [display/World tracking smoke test](../README.md) first.
Actual tag-to-laptop localization also needs a Spectacles Lens that sends
paired device pose + AprilTag observation (or paired camera JPEG/intrinsics)
to the ROS bridge. No such Lens has yet been deployed or tested on this device.
Snap Lens Studio 5.15.4 for Spectacles (2024) is not supported on Ubuntu.
Snap's built-in **Browser Lens** can run a hosted WebXR page without Lens
Studio for a visual/local-tracking experiment. The documented WebXR feature
list does not establish camera-frame access for automatic AprilTag detection
or a working WebSocket-to-ROS pose bridge; those remain untested.

## Run the Ubuntu-only end-to-end mock now

This exercises the real WebSocket bridge, AprilTag registration math, ROS
topics, and TF **without** G1 or physical Spectacles. It cannot test the
glasses' camera, tracking, or display. Docker is used for ROS 2 Humble on this
Ubuntu laptop; it is **not** a Windows Lens Studio container.

From the repository root, open three terminals. The first invocation of the
runner builds a small image from the repository's existing `g1-humble:latest`
image and may take a minute. If that base image is missing, build it with
`docker build -t g1-humble .` (this is a much larger download/build).

Terminal 1 — start the bridge and registration:

```bash
scripts/run_spectacles_laptop.sh
cd /ws/g1_ws
colcon build --packages-select spectacles_localization_ros
source install/setup.bash
ros2 launch spectacles_localization_ros spectacles_localization.launch.py \
  config:=/ws/g1_ws/src/spectacles_localization_ros/config/laptop_anchor.yaml
```

Terminal 2 — send 20 seconds of synthetic glasses poses. The first 25 packets
contain a tag observation; the rest contain device tracking alone:

```bash
scripts/run_spectacles_laptop.sh
cd /ws/g1_ws
source install/setup.bash
ros2 run spectacles_localization_ros laptop_mock_client --count 400
```

Terminal 3 — while terminal 2 is running, inspect the result:

```bash
scripts/run_spectacles_laptop.sh
cd /ws/g1_ws
source install/setup.bash
ros2 topic echo /spectacles/localization_status
ros2 run tf2_ros tf2_echo laptop spectacles
```

The first inspection command keeps printing; press Ctrl-C before running the
second one. You can also watch `/spectacles/pose` in another terminal.

The launch terminal should say `LOCALIZED using 10 detections`; TF should
show `laptop -> spectacles`, and `/spectacles/pose` should continue changing
after the tag observations stop. After terminal 2 finishes, status becomes
`TRACKING_LOST` because no fresh poses are arriving; this is expected.
Restarting the mock client starts a new tracking session and re-registers.
Stop each process with Ctrl-C. All ROS traffic is isolated in domain 77 and
does not connect to or command the G1.

The tag graphic above is for a later **physical** test. USB-C alone does not
stream device pose/camera data into Linux. The planned automatic AprilTag path
needs a deployed Spectacles Lens with camera access; a WebXR-only alternative
would first need proof that its Browser Lens exposes usable camera frames.
With a Lens that implements the documented packet contract, use the
same launch with `bind_host:=0.0.0.0 token:=YOUR_TEST_TOKEN`, put glasses and
laptop on the same isolated Wi-Fi, and have the Lens send to
`ws://<laptop-LAN-IP>:8765`. This plaintext development channel is not for
public networks. Verify the Snap-to-ROS axes, camera-to-device transform, and
capture-time pose pairing before treating a physical pose as metric truth.
See the [architecture contract](../../docs/spectacles_localization_architecture.md).

## Why not Windows Docker or a VM here?

Docker on Linux shares the Linux kernel and cannot run the Windows Lens Studio
GUI. Wine is unsupported by Snap for this workflow. A full Windows VM would
need a Windows installation, suitable GPU/USB passthrough, and hardware
virtualization; this laptop currently exposes no `/dev/kvm`. A borrowed
Windows 11 or macOS computer is the most reliable one-time deployment route.
After deployment, the Ubuntu laptop can remain the ROS localization host.
For an immediate on-device AR smoke test without any editor, open the built-in
**Browser Lens** in Spectacles Lens Explorer and visit one of Snap's
[WebXR demo URLs](https://developers.snap.com/spectacles/about-spectacles-features/webxr).
This tests display and local AR tracking, **not** laptop-frame localization.
